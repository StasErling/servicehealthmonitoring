# Агентный мониторинг здоровья сервисов

## Задача

Разработайте систему наблюдения за локальными сервисами Linux-машины. Сервисы могут не иметь публичного HTTP-адреса или внешнего сетевого порта: проверки выполняет агент внутри машины, который самостоятельно отправляет результаты на центральный сервер.

Пользователь должен понимать, работает ли сервис, удалось ли его проверить и насколько свежи полученные сведения. Запущенный процесс не всегда означает исправное приложение, а молчание агента не доказывает неисправность сервиса.

## Среда и технологии

- Команда: 4–5 человек. Срок проекта — 6–8 недель.
- Эталонная ОС — **Ubuntu Server 24.04 LTS**, полноценная ВМ с systemd. Поддержка других ОС не обязательна, гипервизор — на выбор команды.
- Язык программирования, фреймворки и БД выбирает команда. Готовые библиотеки разрешены; агент и прикладную логику нужно реализовать самостоятельно.
- Агент запускается как systemd-служба. Центральное приложение — через Docker Compose с сохранением данных между перезапусками; БД может быть встроенной или отдельным сервисом.
- Достаточно одной наблюдаемой ВМ. Центральный сервер может работать на ней же.
- Входящие подключения к наблюдаемым сервисам извне не требуются.

## Три типа проверок

| Тип | Что проверяется |
|---|---|
| systemd | Находится ли заданная служба в рабочем состоянии `active` |
| Локальный HTTP | Отвечает ли заданный URL за допустимое время с ожидаемым HTTP-кодом |
| Свежесть файла | Существует ли файл и обновлялся ли он в пределах заданного времени |

Для работы с системой используйте небольшой учебный сервис или генератор: systemd-службу, локальный HTTP endpoint и периодически обновляемый файл. Это вспомогательный компонент, а не отдельный большой проект.

## Обязательная функциональность

### Агент

1. Получает из конфигурации ID машины, адрес сервера, токен и список проверок с устойчивыми ID и параметрами.
2. Выполняет все три типа проверок. Для основной версии достаточно общего интервала, например 20 секунд.
3. Ограничивает длительность HTTP-запросов и внешних вызовов. Ошибка одной проверки не останавливает остальные.
4. Периодически отправляет сообщение о связи и новые результаты проверок с короткими пояснениями. Их можно передавать одним запросом.
5. Продолжает работать при временной недоступности центрального сервера.

### Центральный сервер и панель

1. Проверяют токен и структуру сообщений, хранят результаты и историю изменений состояний.
2. Показывают машины, проверки, последние результаты, пояснения и время обновления.
3. Независимо определяют свежесть связи с агентом и свежесть результата каждой проверки.
4. Сохраняют принятые данные после перезапуска сервера.

## Состояния и их смысл

У каждой проверки есть результат:

- **OK** — проверка выполнена, условие соблюдено.
- **FAIL** — проверка выполнена и обнаружила проблему: служба остановлена, HTTP не ответил вовремя, файл отсутствует или устарел.
- **ERROR** — получить результат не удалось, например из-за недостаточных прав или ошибочной конфигурации. Сделать вывод о здоровье сервиса нельзя.

Отдельно показывается актуальность сведений: «ожидаем первое сообщение», «данные актуальны», «нет свежих данных». Ожидаемые агенты задаются конфигурацией сервера. Пороги давности настраиваются; например, при интервале отправки 20 секунд порог отсутствия связи может составлять 90 секунд.

Давность связи считается по серверному времени приёма. Повторная отправка старого результата не делает проверку свежей: предусмотрите идентификатор или время выполнения результата и опишите выбранный механизм.

Если агент давно молчит, последний OK отображается как **последний известный**, а не как текущее подтверждение исправности. Если агент на связи, но результат одной проверки перестал обновляться, устаревшей становится именно эта проверка.

## Границы проекта

- Достаточно одной машины и трёх проверок. Добавление машины или проверки поддерживаемого типа не должно требовать изменения кода.
- Анализ тела HTTP-ответа, произвольные shell-команды, система плагинов и автоматический перезапуск сервисов не обязательны.
- Проверки не должны требовать запуска всего агента от root. Необходимые разрешения опишите в инструкции.
- Очередь результатов при потере сети не требуется: допустим пробел в истории.
- Токен задаётся конфигурацией и не хранится в Git. Для изолированного учебного стенда допустим HTTP; публичное размещение, TLS и пользовательские роли не обязательны.
- Готовая платформа мониторинга не заменяет собственное приложение.

## Что должно получиться

- Агент, центральный сервер с хранилищем и простая веб-панель.
- Git-репозиторий с историей работы команды и использованием веток/PR.
- README с архитектурой, правилами классификации результатов и устаревания данных, ограничениями.
- Docker Compose, инструкция установки агента, пример systemd unit-файла и конфигурации без секретов.
- Инструкция запуска учебного сервиса или генератора; CI со сборкой или проверкой запуска и автоматическими тестами основной логики.

## Необязательные расширения

После завершения основной функциональности можно добавить уведомления, открытие инцидента после нескольких последовательных неудач или ещё один конкретный тип проверки. Выберите одно направление, если остаётся время.
