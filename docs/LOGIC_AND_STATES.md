# Логика работы и состояния системы

Этот документ описывает бизнес-логику системы мониторинга: типы проверок, матрицу состояний и алгоритм расчета актуальности (свежести) данных. Документ служит контрактом между компонентами системы и исключает разногласия в интерпретации результатов.

---

## 1. Типы проверок

Агент выполняет три типа проверок для каждого настроенного сервиса. Каждая проверка имеет уникальный `check_id` в конфигурации.

### 1.1. Проверка systemd-службы

**Цель**: Убедиться, что заданная systemd-служба находится в рабочем состоянии.

**Механизм**:
- Агент выполняет команду `systemctl is-active <service_name>` или читает статус через D-Bus API systemd.
- Проверяется поле `ActiveState` юнита.

**Результаты**:
| Возвращаемое значение systemd | Состояние проверки |
|-------------------------------|-------------------|
| `active` | OK |
| Ошибка доступа, служба не найдена | ERROR |
| `inactive`, `failed`, `deactivating`, `activating`, или иной ответ | FAIL |

**Пример конфигурации**:
```yaml
checks:
  - id: nginx_service
    type: systemd
    service_name: nginx.service
```

---

### 1.2. Проверка локального HTTP

**Цель**: Убедиться, что локальный HTTP-эндпоинт отвечает в пределах допустимого времени с ожидаемым кодом ответа.

**Механизм**:
- Агент выполняет HTTP-запрос (GET по умолчанию) к заданному URL (например, `http://localhost:8080/health`).
- Измеряется время ответа и проверяется HTTP-код.

**Параметры**:
- `url` — адрес эндпоинта (обязательно).
- `expected_status` — ожидаемый HTTP-код (по умолчанию 200).
- `timeout_ms` — максимальное время ожидания ответа (по умолчанию 5000 мс).

**Результаты**:
| Условие | Состояние проверки |
|---------|-------------------|
| HTTP-код = `expected_status` и время ответа <= `timeout_ms` | OK |
| HTTP-код != `expected_status` или таймаут | FAIL |
| Ошибка сети (DNS, соединение), недоступность хоста | ERROR |

**Пример конфигурации**:
```yaml
checks:
  - id: app_health
    type: http
    url: http://localhost:8080/health
    expected_status: 200
    timeout_ms: 3000
```

---

### 1.3. Проверка свежести файла (touch-файл)

**Цель**: Убедиться, что заданный файл существует и обновлялся в пределах допустимого времени.

**Механизм**:
- Агент проверяет наличие файла по заданному пути.
- Читает метаданные файла (время последней модификации `mtime`).
- Сравнивает `mtime` с текущим временем агента.

**Параметры**:
- `path` — абсолютный путь к файлу (обязательно).
- `max_age_seconds` — максимальный допустимый возраст файла в секундах (по умолчанию 60).

**Результаты**:
| Условие | Состояние проверки |
|---------|-------------------|
| Файл существует и `(текущее_время - mtime) ≤ max_age_seconds` | OK |
| Файл существует, но `(текущее_время - mtime) > max_age_seconds` | FAIL |
| Файл не существует, ошибка доступа (permissions) | ERROR |

**Пример конфигурации**:
```yaml
checks:
  - id: cron_job_marker
    type: file_freshness
    path: /var/run/myapp/last_run.marker
    max_age_seconds: 300
```

## 2. Матрица состояний проверок

Каждая проверка может находиться в одном из трех состояний:

### 2.1. OK (Норма)
**Определение**: Проверка выполнена успешно, условие соблюдено.

**Примеры**:
- systemd-служба активна (`active`).
- HTTP-эндпоинт вернул 200 за 120 мс.
- Файл обновлялся 10 секунд назад (при пороге 60 сек).

**Отображение в UI**: Зеленый индикатор.

---

### 2.2. FAIL (Проблема)
**Определение**: Проверка выполнена, но обнаружила проблему. Сервис работает некорректно.

**Примеры**:
- systemd-служба остановлена (`inactive`) или упала (`failed`).
- HTTP-эндпоинт вернул 500 или не ответил за 5 секунд.
- Файл не обновлялся 10 минут (при пороге 60 сек).

**Отображение в UI**: Красный индикатор.

**Действия системы**:
- Центральный сервер регистрирует инцидент.
- Если настроены уведомления — отправляется алерт.
- В истории состояний создается запись о переходе из OK в FAIL.

---

### 2.3. ERROR (Ошибка проверки)
**Определение**: Получить результат проверки не удалось. Сделать вывод о здоровье сервиса **нельзя**.

**Примеры**:
- Агент не имеет прав на чтение статуса systemd-службы.
- Ошибка конфигурации (неверный путь к файлу, некорректный URL).
- Внутренняя ошибка агента (нехватка памяти, сбой таймера).

**Отображение в UI**: Желтый индикатор с пометкой "Ошибка проверки".

**Важно**: ERROR != FAIL. Это означает, что мы **не знаем** состояние сервиса, а не то, что он сломан.

## 3. Логика "свежести" данных (Freshness)

Это ключевая часть системы. Пользователь должен понимать, насколько актуальны отображаемые данные.

### 3.1. Два уровня свежести

Система отслеживает два независимых показателя:

1. **Свежесть связи с агентом** (Agent Freshness) — когда агент последний раз выходил на связь.
2. **Свежесть результата проверки** (Check Freshness) — когда конкретная проверка последний раз выполнялась и возвращала результат.

---

### 3.2. Свежесть связи с агентом

**Определение**: Время, прошедшее с момента последнего успешного получения данных от агента (любой посылки, включая heartbeat).

**Расчет**:
```
agent_freshness_seconds = server_current_time - last_agent_heartbeat_time
```

**Пороговые значения** (настраиваются в конфигурации сервера):
| Порог | Статус | Описание |
|-------|--------|----------|
| `<= 90 секунд` |  Актуально | Агент на связи, данные свежие. |
| `90–300 секунд` | Подозрительно | Агент молчит, возможно проблема с сетью. |
| `> 300 секунд` |  Нет связи | Агент отвалился или машина недоступна. |

**Пример**:
- Интервал отправки агента: 20 секунд.
- Порог "нет связи": 90 секунд (4.5 пропущенных цикла).
- Если агент не присылал данные 2 минуты -> статус "Подозрительно".

---

### 3.3. Свежесть результата проверки

**Определение**: Время, прошедшее с момента последнего выполнения конкретной проверки на агенте.

**Расчет**:
```
check_freshness_seconds = server_current_time - check_execution_timestamp
```

**Важно**: Используется **timestamp выполнения проверки на агенте**, а не время приема на сервере. Это критично для корректной работы с очередью (см. `ARCHITECTURE.md`, раздел 3.5).

**Пороговые значения** (настраиваются для каждой проверки индивидуально, по умолчанию = интервал проверки × 3):
| Порог | Статус | Описание |
|-------|--------|----------|
| `<= порог` | Актуально | Проверка выполнялась недавно. |
| `> порог` |  Устарело | Проверка не выполнялась давно, данные ненадежны. |

**Пример**:
- Интервал проверки: 20 секунд.
- Порог устаревания: 60 секунд.
- Если проверка не выполнялась 2 минуты -> статус "Устарело".

---

### 3.4. Комбинированный статус в UI

Пользователь видит комбинированный статус, который учитывает оба уровня свежести:

| Свежесть агента | Свежесть проверки | Результат проверки | Итоговый статус |
|-----------------|-------------------|-------------------|-----------------|
| Актуально | Актуально | OK | **Работает** |
| Актуально | Актуально | FAIL | **Проблема** |
| Актуально | Актуально | ERROR | **Ошибка проверки** |
| Актуально | Устарело | OK (старый) | **Последний известный OK** |
| Подозрительно | Устарело | Любой | **Нет свежих данных** |
| Нет связи | Устарело | Любой | **Агент недоступен** |

**Ключевое правило**: Если агент на связи, но конкретная проверка не обновлялась — устаревшей считается **именно эта проверка**, а не все данные с машины.

## 4. Обработка пограничных случаев

### 4.1. Первый запуск агента

**Ситуация**: Агент только установлен, сервер еще не получил ни одной посылки.

**Статус**: "Ожидаем первое сообщение" (серый индикатор).

**Действие**: Сервер показывает конфигурацию машины, но все проверки помечены как "Нет данных".

---

### 4.2. Агент отправляет старый результат из очереди

**Ситуация**: Агент был offline 10 минут, восстановил связь и отправил накопленные посылки.

**Обработка на сервере**:
1. Сервер принимает посылку с `timestamp = 10 минут назад`.
2. Записывает результат в БД с оригинальным timestamp.
3. Рассчитывает свежесть по формуле: `server_current_time - check_execution_timestamp = 10 минут`.
4. Статус проверки: "Устарело" (если порог < 10 минут).

**Отображение в UI**: Показывается результат с пометкой "Результат от [время]", индикатор свежести — желтый.

---

### 4.3. Повторная отправка того же результата

**Ситуация**: Агент отправляет тот же результат проверки (без изменений) в следующем цикле.

**Правило**: Каждый результат имеет уникальный идентификатор (например, `check_execution_id` или точный timestamp с миллисекундами). Сервер игнорирует дубликаты.

**Цель**: Избежать "накрутки" свежести за счет повторной отправки старых данных.

---

### 4.4. Часовые пояса и синхронизация времени

**Проблема**: Агент и сервер могут находиться в разных часовых поясах.

**Решение**:
- Все timestamp'ы передаются в формате **Unix timestamp (UTC)** или **ISO 8601 с указанием часового пояса** (например, `2026-11-24T10:30:00Z`).
- Сервер всегда использует свое локальное время (UTC) для расчета свежести.
- Агент синхронизирует время через NTP (рекомендация в `DEPLOYMENT.md`).

## 5. Примеры сценариев

### Сценарий 1: Нормальная работа

```
T=0:   Агент выполняет проверки -> все OK -> отправляет на сервер
T=20:  Агент выполняет проверки -> все OK -> отправляет на сервер
T=40:  Агент выполняет проверки -> все OK -> отправляет на сервер

Статус в UI: Работает (свежесть: 40 сек)
```

---

### Сценарий 2: Служба упала

```
T=0:   Агент: nginx=OK, app=OK -> отправляет
T=20:  Агент: nginx=FAIL (stopped), app=OK -> отправляет
T=40:  Агент: nginx=FAIL, app=OK -> отправляет

Статус в UI:
  - nginx: Проблема (свежесть: 40 сек)
  - app: Работает (свежесть: 40 сек)
```

---

### Сценарий 3: Агент отвалился

```
T=0:   Агент: все OK -> отправляет
T=20:  Агент: все OK -> отправляет
T=40:  [Агент crashed или сеть обрыв]
T=60:  [Тишина]
T=90:  [Тишина]
T=120: [Тишина]

Статус в UI (на T=120):
  - Свежесть агента: 120 сек -> Подозрительно
  - nginx: Последний известный OK (от T=20, свежесть 100 сек)
  - app: Последний известный OK (от T=20, свежесть 100 сек)
```

---

### Сценарий 4: Восстановление после сбоя с очередью

```
T=0:   Агент: все OK -> отправляет
T=20:  Агент: все OK -> [сервер недоступен] -> сохраняет в очередь
T=40:  Агент: nginx=FAIL -> [сервер недоступен] -> сохраняет в очередь
T=60:  [Сервер восстановлен]
T=61:  Агент: отправляет посылки за T=20 и T=40 из очереди
T=62:  Агент: выполняет свежие проверки -> отправляет

Статус в UI (на T=62):
  - Свежесть агента: 2 сек -> Актуально
  - nginx: Проблема (результат от T=40, свежесть 22 сек)
  - app: Работает (результат от T=62, свежесть 0 сек)
```
